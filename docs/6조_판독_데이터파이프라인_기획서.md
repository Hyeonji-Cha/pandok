# 판독(PANDOK) 개인 프로젝트 계획서

> 기간: 2026-08-31 ~ 2026-09-08  
> 유형: 개인 데이터 엔지니어링 학습 프로젝트  
> 주제: **Steam 게임 로그 기반 실시간·배치 데이터 파이프라인 및 AI 게임 분석 리포트 구축**  
> 대상 게임: **King Charles: Rise of the Alpha**  
> AWS: Sydney, `ap-southeast-2`

## 1. 프로젝트 개요

판독(PANDOK)은 Steam 게임 **King Charles: Rise of the Alpha**에서 생성되는 동의 기반 gameplay log를 대상으로, 실시간 수집과 배치 분석을 함께 학습하는 개인 데이터 엔지니어링 프로젝트다. 한 번의 플레이 단위인 Run에서 발생하는 시작, 60초 checkpoint, upgrade option 노출, upgrade 선택, Run 종료 이벤트를 수집하고 중복·누락·순서 역전을 처리해 Bronze·Silver·Gold 데이터로 발전시킨다.

분석 대상은 플레이어 개인이나 Steam 계정이 아니라 **익명화된 개별 Run과 여러 Run에서 집계된 gameplay 경향**이다. 이를 통해 다음과 같은 게임 진행 특성을 확인한다.

- 플레이어가 어느 checkpoint와 level 구간까지 도달하는지
- XP, HP, kill, gold가 Run 진행에 따라 어떻게 변하는지
- 어떤 upgrade option이 노출되고 실제로 선택되는지
- Run이 사망, 종료, 재시작 또는 완료 중 어떤 이유로 끝나는지
- retry, 누락 또는 잘못된 순서 때문에 신뢰할 수 없는 Run이 얼마나 발생하는지

데이터의 직접 사용자는 게임 운영 고객이 아니라 프로젝트를 수행하는 **개인 데이터 엔지니어**다. 최종 결과물은 데이터 계약, 수집·정제 파이프라인, 분석용 집계 지표, 품질 검증 결과와 게임 개발자가 참고할 수 있는 AI 분석 리포트의 기술적 시제품이다. AI 리포트는 검증된 Gold 집계만 입력으로 사용하며 게임을 자동 변경하지 않는다.

```text
Unity
  -> Türkiye Gateway
  -> 개인정보 제거·v2 Schema 검증·중복 처리
  -> PANDOK v2 Run 이벤트
  -> AWS Sydney Bronze
  -> Silver Run 복원
  -> Gold 집계·분석
```

AWS 주 입력 계약은 `telemetry-event-v2`다. Gateway 폴더의 `aggregate-export-v1`은 선택적 대조 자료이며 v2를 대체하지 않는다.

|---|---|

## 2. 프로젝트 배경과 학습 목적

게임 telemetry는 retry, 도착 순서 변경, 누락 및 잘못된 값 때문에 그대로는 신뢰하기 어렵다. Steam 계정, IP, 기기 또는 장기 식별자를 수집하면 학습 목적보다 큰 개인정보 위험도 만든다.

이 프로젝트에서 학습·검증할 내용은 다음과 같다.

- JSON Schema 기반 데이터 계약과 버전 관리
- 분석 영역에 들어오기 전 개인정보를 차단하는 Privacy-by-Design
- retry 중복 제거와 Run 상태 복원
- Bronze·Silver·Gold 계층 설계
- S3, Glue Data Catalog, Athena 기반 serverless 분석
- Terraform 인프라 재현, 자동 테스트, 데이터 품질과 비용 제한

## 3. 프로젝트 목표

1. 익명 v2 이벤트 계약을 코드와 테스트로 고정한다.
2. `run_id`, `event_id`, `event_sequence`, `run_elapsed_seconds`로 Run을 복원한다.
3. 사용자·Steam 계정·Session·IP·기기정보·정확한 `event_time`을 AWS 입력에서 거부한다.
4. `CONSENTED_PROD_PLAY`, `CONTROLLED_SCENARIO`, `LOAD_TEST`를 분리한다.
5. retry는 한 번만 반영하고 누락 Run과 잘못된 Run을 구분한다.
6. AWS 배포 전 `CONTROLLED_SCENARIO`로 로컬 흐름을 검증한다.
7. 최소 AWS 경로에서 Bronze 저장과 Athena 분석을 재현한다.

## 5. 핵심 지표

아래 지표는 [v2 Schema](../contracts/telemetry-event-v2.schema.json)의 실제 필드로 계산할 수 있다.

| 지표 | 계산 기준 | 실제 필드 | 가능 여부 |
|---|---|---|---|
| Run 종료 사유 비율 | `end_reason`별 종료 수 / 전체 종료 수 | `event_name`, `end_reason` | 가능 |
| 평균 Run 지속시간 | `run_ended.run_elapsed_seconds` 평균 | `run_elapsed_seconds` | 가능 |
| Run 완료율 | `end_reason=run_completed` / 전체 종료 Run | `end_reason` | 가능 |
| checkpoint 평균 level | checkpoint별 평균 | `checkpoint_number`, `player_level` | 가능 |
| checkpoint 평균 XP | checkpoint별 평균 | `current_xp`, `xp_to_next_level` | 가능 |
| checkpoint 평균 HP | checkpoint별 평균 | `hp_percent` | 가능 |
| checkpoint 평균 kill | checkpoint별 평균 | `total_kills` | 가능 |
| checkpoint 평균 gold | checkpoint별 평균 | `current_gold` | 가능 |
| upgrade option 노출 수 | `options[]`의 item별 count | `options[].item_id` | 가능 |
| upgrade 선택 수 | item별 count | `selected_item_id` | 가능 |
| option 대비 선택 비율 | 선택 수 / 동일 조건 노출 수 | `choice_id`, item·rarity·slot | 가능 |
| 중복 이벤트 수 | 전체 수 - 고유 `event_id` 수 | `event_id` | 가능 |
| Run 상태 수와 비율 | validator 상태별 count | `VALID/INCOMPLETE/INVALID` | 로컬 가능, Gold 예정 |

Run 시작 대비 종료 비율은 완전성 지표이고 `run_completed` 비율과는 다르다. product 지표는 `source_type=CONSENTED_PROD_PLAY`만 포함한다. 실제 플레이 데이터가 저장소에 없으므로 현재는 계산 가능성만 확인됐다.

## 6. 이벤트 및 데이터 계약

주 계약은 [telemetry-event-v2.schema.json](../contracts/telemetry-event-v2.schema.json)이며 JSON Schema Draft 2020-12를 사용한다.

| 이벤트 | 역할 | 주요 필드 |
|---|---|---|
| `upgrade_options_shown` | 실제 노출 선택지 | `choice_id`, `choice_source`, `options` |
| `upgrade_selected` | 노출과 실제 선택 연결 | `choice_id`, `selected_item_id`, `selected_rarity` |
| `run_started` | active gameplay 시작 | `map_id`, `starting_max_hp`, `starting_weapon_id` |
| `run_checkpoint` | 60초 단위 누적 상태 | level, XP, HP, kill, gold, upgrades |
| `run_ended` | 종료 이유·최종 누적 상태 | `end_reason`, duration, level, kill, gold |

공통 필드는 `event_id`, `event_name`, `source_type`, `run_id`, `event_sequence`, `run_elapsed_seconds`, `game_version`, `schema_version=2.0`이다. 정확한 retry는 동일 `event_id`와 payload를 유지한다.

## 7. 개인정보 보호 설계

- 동의 후에만 telemetry를 생성·전송하고 철회 시 pending queue를 삭제한다.
- Game Client는 Türkiye Gateway로만 보내고 AWS endpoint·credential을 포함하지 않는다.
- `run_id`는 매 Run 새로 생성하고 플레이어·다른 Run과 매핑하지 않는다.
- `anonymous_user_id`, `session_id`, `session_started`, client `event_time`은 AWS로 보내지 않는다.
- validator는 계정·기기·네트워크·인증 key를 표기 변형과 중첩 위치까지 검사한다.
- `CONSENTED_PROD_PLAY`은 `turkiye_gateway` channel에서만 허용한다.

Gateway 문서에는 실제 client 연결, opt-in, deduplication, raw body 미저장과 access log 비활성화가 완료됐다고 적혀 있다. 이는 저장소 문서상 상태이며 외부 VPS 설정을 이 저장소만으로 독립 검증한 결과는 아니다.

## 8. 전체 아키텍처 및 ETL 데이터 흐름

### 8.1 전체 아키텍처

```text
[데이터 생성]
Unity Game Client
  - 명시적 telemetry 동의
  - Run event 생성
  - 실패 event의 local queue·retry
        |
        | HTTPS
        v
[개인정보 경계]
Türkiye Gateway
  - client IP·원본 network header 제거
  - 허용된 v2 field로 payload 재구성
  - JSON Schema·privacy validation
  - 동일 event retry 중복 처리
        |
        | 익명 PANDOK v2 Run event
        v
[AWS Sydney 수집·저장]
Ingestion boundary
  - source_type / ingestion_channel 검증
  - AWS received_at metadata 추가
        |
        v
S3 Bronze JSON
  - 검증 event 원형 보존
  - 재처리 원본과 도착 증적
        |
        v
[정제·Run 복원]
Silver ETL
  - event_id deduplication
  - event_sequence 정렬
  - shown-selected 연결
  - 누적 counter·checkpoint 검증
  - VALID / INCOMPLETE / INVALID 분류
        |                     \
        v                      -> Quarantine + 오류 사유
S3 Silver Parquet
        |
        v
[집계·분석]
Glue Data Catalog -> Athena batch SQL
  - CONSENTED_PROD_PLAY 필터
  - Run 종료·checkpoint·upgrade 집계
        |
        v
S3 Gold / Athena View
        |
        v
[활용]
검증된 핵심 지표 -> AI 게임 분석 리포트 -> 개발자 검토
```

이 구조에서 Unity와 Türkiye Gateway는 데이터 생성·개인정보 경계이고, AWS Sydney 이후가 판독의 데이터 엔지니어링 영역이다. 별도 운영 DB 없이 S3를 저장 계층으로 사용하며 Glue Data Catalog와 Athena가 batch 분석을 담당한다.

### 8.2 실시간 처리 경로

실시간 경로의 목적은 event가 발생한 직후 계약을 검사하고 안전한 Bronze 원본을 남기는 것이다.

```text
Unity event
-> Türkiye Gateway privacy transformation
-> AWS ingestion validation
-> Bronze append
```

초기 최소 구현은 요청 단위 validation 후 S3에 적재하는 방식이다. Kinesis·Firehose·Managed Flink는 높은 처리량이 필요해서가 아니라 streaming buffer, watermark, late event 처리를 학습하기 위한 선택적 확장이다. 따라서 9일 범위에서는 필수 구성으로 간주하지 않는다.

### 8.3 배치 ETL 경로

```text
Extract
  S3 Bronze에서 날짜 범위의 v2 JSON event 읽기
        |
Transform
  Schema 재확인
  -> event_id retry 제거
  -> run_id별 grouping
  -> event_sequence 정렬
  -> choice·checkpoint·counter 검증
  -> Run 상태 결정
  -> 분석 가능한 column 형태로 변환
        |
Load
  Silver Parquet와 Quarantine 적재
        |
Aggregate
  Athena SQL로 product source 필터·핵심 지표 계산
        |
Load
  Gold table/view와 AI report 입력 dataset 생성
```

| ETL 단계 | 입력 | 핵심 처리 | 출력 | 실행 방식 |
|---|---|---|---|---|
| Extract | Türkiye Gateway의 익명 v2 event | JSON parsing, metadata 생성 | Bronze record | event 단위 실시간 |
| Bronze Load | 검증 event | 변경 없이 append, 30일 lifecycle | S3 Bronze JSON | 실시간 또는 micro-batch |
| Silver Transform | 날짜별 Bronze | deduplication, Run 복원, 품질 판정 | trusted event·Run, Quarantine | 예약 batch |
| Silver Load | 정제 결과 | columnar·partition 저장 | S3 Silver Parquet | 예약 batch |
| Gold Transform | Silver | product filter, 지표별 group·aggregate | Run·checkpoint·upgrade 지표 | Athena batch SQL |
| Report Load | 검증 Gold | metric ID·값·근거만 선별 | AI report input·Markdown report | 일회 또는 일별 batch |

### 8.4 현재 구현과 목표 아키텍처의 차이

| 구간 | 현재 상태 | 목표 상태 |
|---|---|---|
| Producer | CONTROLLED_SCENARIO generator 구현 | Unity v2 event 연동 |
| Privacy boundary | Gateway 문서·참고 구현 존재 | 실제 outbound header·log 증적 확보 |
| Ingestion | 로컬 JSON -> Bronze envelope 구현 | AWS ingest -> S3 Bronze |
| Bronze | S3 Terraform 작성, 미배포 | synthetic event 저장·조회 |
| Silver | Python validator로 Run 복원 규칙 구현 | 날짜별 Parquet ETL |
| Gold | 지표 정의 완료 | Athena SQL과 Gold dataset |
| AI report | 입력 원칙만 정의 | 검증 Gold 기반 리포트 시제품 |

현재 자동 테스트가 검증하는 실제 로컬 흐름은 다음과 같다.

```text
v2 fixture -> CONTROLLED_SCENARIO generator -> JSON
-> ingest_json() -> v2/privacy validation
-> source/channel 검사 -> Bronze envelope
-> validate_anonymous_sequence()
```

## 9. Bronze·Silver·Gold 역할

| 계층 | 역할 | 상태 |
|---|---|---|
| Bronze | 검증 v2 event와 `received_at`, channel 보존 | envelope 구현, S3 Terraform 작성 |
| Silver | deduplication, sequence 정렬, choice 연결, Run 복원 | validator 규칙 구현, table 미구현 |
| Gold | product source만 사용한 종료·checkpoint·upgrade 집계 | 계획 |
| Quarantine | invalid/conflict/too-late 사유 관리 | 계획 |

## 16. 데이터 품질 기준

- 모든 event는 v2 Schema를 통과한다.
- 한 Run의 `run_id`, `game_version`, `schema_version`, `source_type`은 같다.
- `event_sequence`가 논리 순서를 결정한다.
- 동일 `event_id`·payload는 retry, 다른 payload는 conflict다.
- checkpoint는 `checkpoint_number × 60 = run_elapsed_seconds`다.
- cumulative field는 감소하지 않는다.
- product Gold에는 `CONSENTED_PROD_PLAY`만 포함한다.
- 계층별 count 차이는 사유별 설명이 가능해야 한다.

## 17. 실패·재시도·중복·불완전 Run

| 상황 | 판정·처리 |
|---|---|
| 같은 `event_id`·payload | retry, 한 event로 deduplicate |
| 같은 `event_id`·다른 payload | `DUPLICATE_CONFLICT`, `INVALID` |
| sequence gap 또는 종료 없음 | `INCOMPLETE` |
| shown 없이 selected | 현재 `INCOMPLETE` |
| 같은 sequence에 다른 event | `INVALID` |
| elapsed/counter 감소 | `INVALID` |
| 종료 뒤 event | `INVALID` |
| schema/privacy 오류 | Bronze 전 거부 |

timeout과 실제 streaming watermark는 아직 구현하지 않았다.
